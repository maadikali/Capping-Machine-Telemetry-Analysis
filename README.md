# Capping Machine Telemetry Analysis

This project is based on a real dataset I worked with from an industrial capping line (a multi head bottle/container capping machine). I can't share the original data since it's confidential, so I rebuilt the same structure and column schema myself and generated synthetic data that behaves the same way. That way the pipeline and the analysis are fully reproducible without exposing anything from the real production line.

The raw export is a noisy, high frequency polling stream, not clean event level data. Before I could do any real analysis, I had to turn it into an actual event log. That meant figuring out which polling rows correspond to a real capping cycle, mapping the status codes into something usable, and only then looking at quality, throughput, and machine behaviour.

## What's in the analysis

- data quality checks (missing/invalid values, schema issues)
- reconstructing real capping events out of the raw polling rows
- overall and per head success rate
- rejects, faults, and no load cycles handled separately
- torque distributions and out of range values
- torque variability between heads
- production trends and rolling averages
- torque drift over time
- idle / no load periods
- capping speed (throughput)
- torque vs. closure quality
- comparing individual heads against the rest of the line

## Why event reconstruction is the hard part

The machine is polled much more often than it actually completes a capping cycle, so one real closure event shows up across several consecutive rows for the same head. If I computed KPIs directly on the raw rows, I would massively over count activity, since every head "cycles" dozens of times per second when it's really done once.

The fix I used was to track each head's `Count` value and treat every increase as exactly one new closure event. That collapses the wide polling table into a clean, one row per event dataset that everything else is built on.

I also mapped each event's status code into four categories, since the raw codes on their own aren't very useful for analysis:

- **success**: a valid closure
- **no_load**: the head cycled with no bottle present, not a real attempt
- **reject**: a closure was attempted but failed the quality signal
- **fault**: a machine/diagnostic issue, distinct from a quality reject

I excluded no load events from the success rate denominator since they're not real attempts. I also kept rejects and faults separate instead of lumping them together, since they mean different things operationally.

## Notebook

The whole analysis is in `notebooks/analysis.ipynb`, and it follows one order:

raw data, then data quality, then event reconstruction, then KPIs, then quality analysis, then trends, then idle time, then correlation, then conclusions.

The notebook is where the analysis actually happens. The reusable logic behind it (cleaning, event detection, KPI/trend/anomaly/correlation functions) lives in `src/capping_telemetry/`, so it's unit tested instead of just being copy pasted into notebook cells.

## Project structure

```text
capping-machine-telemetry/
├── notebooks/
│   └── analysis.ipynb          the full analysis, start to finish
│
├── src/capping_telemetry/      reusable analysis code behind the notebook
│   ├── ingestion/              loading, schema checks, event detection
│   ├── analytics/              KPIs, trends, anomalies, idle time, correlations
│   ├── config.py               configuration loading
│   └── utils/                  logging helper
│
├── data/
│   ├── generate_sample_data.py generates the synthetic dataset below
│   └── pools/sample_pool/      the synthetic telemetry used in the notebook
│
├── config/
│   ├── config.yaml             paths and analysis thresholds
│   └── status_codes.json       reference table for the raw status codes
│
├── tests/                      unit tests for the ingestion/analytics code
├── requirements.txt
└── pyproject.toml
```

## Running it

```bash
pip install -r requirements.txt
jupyter notebook notebooks/analysis.ipynb
```

The notebook adds `src/` to its own path in the first cell, so there's no need to install the package first. Just install the requirements and run it top to bottom.

To run the unit tests instead:

```bash
pip install -e .
pytest
```

## A note on the data

The real dataset this is based on came from an internal analytics project I worked on, and it's not included here for confidentiality reasons. What's in `data/pools/sample_pool/` is synthetic data generated by `data/generate_sample_data.py`, built to match the same schema (36 heads, same status codes, same wide polling format) so the notebook and tests run end to end without needing the original files.
